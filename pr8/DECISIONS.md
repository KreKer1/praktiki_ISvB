## Вариант

Номер варианта: 18

- **Часть А:** R5 — `approve` требует указать руководителя, одобрившего заявку.
  Сигнатура изменена на `BusinessTrip.approve(String approver)` (вариант явно это требует),
  добавлено поле `private String approvedBy`. Пустое или `null` имя → `IllegalArgumentException`,
  статус при этом не меняется.
- **Часть Б:** `addApprover(BusinessTrip trip) → String` возвращает имя руководителя или `null`,
  если заявку не одобряли. Метод размещён в `BusinessTripService`, данные берёт через
  `trip.getApprovedBy()`.

Проверки варианта в `SelfCheck` (№ 19–22): `approve("")` → ошибка и статус остаётся SUBMITTED;
`approve(null)` → ошибка; `addApprover` после одобрения → имя; `addApprover` без одобрения → `null`.
№ 23 проверяет сервис (`create` + `findByStatus`). В `data/sample.csv` добавлены 4 строки варианта (T-16…T-19).

## Решение 1. Порядок проверок в approve: сначала статус, потом имя

**Формулировка.** В `approve(String approver)` сначала проверяется переход (`status != SUBMITTED` →
`IllegalStateException`), затем данные (пустое имя → `IllegalArgumentException`), и только после
обеих проверок присваиваются `approvedBy` и `status`.

**Альтернатива.** Сначала проверять имя, потом статус; или присвоить `approvedBy` до проверок.

**Обоснование.** Так же устроен `reject` из задания (R5, затем R6), поэтому методы единообразны, а
Activity-диаграмма описывает их одним алгоритмом: «допустим ли переход» → «корректны ли данные» →
«изменить состояние». Если вызвать `approve` из DRAFT, пользователь получит главную причину
отказа (неверный статус), а не второстепенную. Присваивание после проверок гарантирует, что при
любой ошибке объект не меняется (ни статус, ни `approvedBy`).

## Решение 2. addApprover — в BusinessTripService, approvedBy — без setter

**Формулировка.** Поле `approvedBy` — `private`, без setter, устанавливается только внутри
`approve`. Метод чтения `addApprover(BusinessTrip)` вынесен в сервис и использует геттер.

**Альтернатива.** Публичный `setApprovedBy(String)` или метод `addApprover()` прямо в `BusinessTrip`.

**Обоснование.** Setter позволил бы указать руководителя у заявки, которую никто не одобрял:
это то же нарушение инкапсуляции, что и `setStatus` (R10). Имя руководителя и статус APPROVED
должны меняться одной доменной операцией. Метод `addApprover` ничего не меняет, а только читает
данные для внешнего потребителя (отдел кадров, отчёты) и принимает заявку параметром, поэтому
естественно относится к сервисному слою, как и `findByStatus`.

## Ответы на контрольные вопросы

### Вопрос 1. Какая проверка защищает от наиболее вероятной ошибки входных данных и где она?

Проверка `start <= end` в конструкторе `BusinessTrip` (правило R2): `if (start.isAfter(end))`
выбрасывает `IllegalArgumentException`. Даты вводятся вручную или приходят из CSV в формате
ГГГГ-ММ-ДД, и перепутать день начала и окончания — самая частая ошибка (в `sample.csv` это строка
T-04). Проверка стоит в конструкторе (fail-fast), поэтому заявка с неверными датами вообще не
создаётся, и все последующие методы, включая `complete` с проверкой `today >= end`, работают
только с корректным периодом. Рядом в конструкторе стоят проверки пустого id (R1) и `null`-дат.

### Вопрос 2. Какой метод или класс содержит ключевое бизнес-правило и почему он там?

Ключевые правила — допустимость переходов R3/R5/R7/R8 — находятся в доменных методах класса
`BusinessTrip`: `submit`, `approve`, `reject`, `cancel`, `complete`. Каждый метод сначала проверяет
текущий `status` и выбрасывает `IllegalStateException`, если переход недопустим. Правила размещены
в модели, потому что только `BusinessTrip` знает свой статус и меняет его сам; поле `status`
закрыто и не имеет setter (R10). Если вынести проверки в `BusinessTripService`, пришлось бы
открыть изменение статуса наружу, и любой код смог бы обойти сервис и перевести заявку,
например, из DRAFT сразу в COMPLETED.

### Вопрос 3. Как Activity-диаграмма отражает конкретный участок кода?

Переход DRAFT → SUBMITTED на правой части диаграммы и блоки «Проверить допустимость перехода» →
«Переход допустим» → «Изменить состояние заявки» соответствуют методу `submit()`. Блок проверки
перехода — это строка `if (status != TripStatus.DRAFT)`, ветка «нет» к блоку «Зафиксировать ошибку»
— `throw new IllegalStateException("Ошибка перехода: " + status + " → SUBMITTED недопустим")`,
ветка «да» — `status = TripStatus.SUBMITTED`. Для `reject` дополнительно срабатывает блок
«Проверить данные операции»: `reason == null || reason.length() < 10` → `IllegalArgumentException`,
и объект при этом не меняется.

### Вопрос 4. Какое изменение требования затронет минимальное число классов и почему?

Изменение минимальной длины причины отклонения с 10 на 20 символов. Меняется одно условие в
методе `BusinessTrip.reject`: `reason.length() < 10` → `< 20` (и текст сообщения). Другие классы
не затрагиваются: `BusinessTripService` и `TripStatus` о причине ничего не знают, а сам переход
SUBMITTED → REJECTED остаётся прежним. Правило локализовано, потому что проверка данных находится
в том же доменном методе, который меняет состояние. Дополнительно обновляются только ожидания
тестов `SelfCheck` (№ 10 с причиной ровно 10 символов) и строки `sample.csv` с REJECT.

## Фрагмент кода для анализа

```java
public void setStatus(TripStatus status) {
    this.status = status;
}
```

Открытый setter нарушает инкапсуляцию: класс больше не контролирует собственное состояние, и
правила переходов R3/R5/R7/R8 перестают действовать. Любой внешний код может вызвать
`trip.setStatus(TripStatus.COMPLETED)` прямо из DRAFT, минуя согласование и проверку даты
окончания (R9), или «оживить» отклонённую заявку через `setStatus(SUBMITTED)`. Исправление —
удалить setter и менять статус только доменными методами `submit()`, `approve(имя)`,
`reject(причина)`, `cancel()`, `complete(дата)`, каждый из которых сначала проверяет допустимость
перехода. Это правило R10: `status`, `rejectionReason` (и в варианте 18 `approvedBy`) объявлены
`private` без setter, поэтому заявка всегда проходит только по разрешённым переходам.
